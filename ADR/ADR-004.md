# Versioned SQLite graph storage with explicit transaction scope

- Decision date: 2026-08-05
- Review calibration: 2026-08-24
- Status: Accepted
- Implementation anchor: `CODE/continuum_db.py`

## Status

Accepted for the bounded reference implementation; broader system claims remain out of scope.

## Context

`GraphDB` is the persistence/storage core. Its guarantees are limited to the SQLite database connection/path actually opened.

## Decision

The current graph schema is version-scoped:

- node key: `(node_id, version)`
- edge key: `(source_id, target_id, relationship, version)`
- edge endpoints reference nodes at the same version
- foreign keys are enabled and verified per connection
- FTS5 is an external-content index synchronized through node insert/delete/update triggers
- node upsert uses `ON CONFLICT ... DO UPDATE`
- savepoint names are validated/quoted before use
- rollback rolls back to and releases the savepoint

`semantic_search()` is lexical FTS5 search with quoted caller text, optional version scope, bounded result count, and deterministic secondary ordering.

`snapshot_digest(version)` hashes sorted nodes/edges for that version.

## `:memory:` boundary

A bare SQLite `:memory:` database belongs to the connection that opened it and disappears when that connection closes.

Therefore a task using the default `GraphDB()` cannot establish cross-task, cross-process, or cross-day persistence unless a shared/durable store identity is separately evidenced.

## Consequences

Callers receive an inspectable local contract but remain responsible for deployment, authority, persistence, and claims outside the named implementation surface.

## Verification

Verification requires a named repository path, revision, fixture or store identity, command, environment, exit code, and retained failures. Documentary review alone is not runtime or semantic validation.

## Evidence boundary

A snapshot digest can establish identity of the represented versioned snapshot under this serialization contract. It does not prove that the same durable object existed through an unobserved interval.

A successful write/read on one connection does not establish visibility from another connection.

This ADR does not claim distributed storage, replication, backup, authentication, encryption, or production durability.
