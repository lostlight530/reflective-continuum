# Standard-library runtime and explicit contracts

- Decision date: 2026-08-05
- Review calibration: 2026-08-24
- Scope: reflective-continuum storage, analysis, validation, tasks, and verification

## Status

Accepted.

- Supersedes named ADR: `NONE`
- Historical correction scope: replaces earlier absolute or unverifiable repository prose about dependency minimalism and correctness; no predecessor file is asserted

## Context

A small auditable core is valuable, but “zero dependency” cannot establish correctness or security.

## Decision

Runtime code uses the Python standard library only. Formats and errors are explicit contracts. Python-version compatibility is a revision- and evidence-specific claim: a version is supported only to the extent that the relevant commands/tests were actually executed and their results were retained. ADR prose is never executable configuration.

## Consequences

Low supply-chain surface; callers still own SQLite build features and deployment controls. Documentation must not infer compatibility from a test file, workflow file, historical sentence, or model-generated completion claim.

## Verification

Record the actual verification surface used for the relevant change: commands, Python/SQLite versions, fixture or digest, result, and untested boundary. FTS5/selfcheck/AST/test evidence supports only the revision and configuration actually checked. Documentation-only maintenance explicitly records when no tests were run.

No CI or test matrix is implied by this ADR.

## Exceptions

An exception requires owner, expiry, affected failure/threat model, compensating control, test or evidence plan when applicable, migration when relevant, and rollback in a reviewed pull request.
