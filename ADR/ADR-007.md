# Executable policy lives in RuleConfig and RuleEngine, not prose

- Decision date: 2026-08-05
- Review calibration: 2026-08-24
- Status: Accepted
- Implementation anchor: `CODE/reflective_validator.py`

## Status

Accepted for the bounded reference implementation; broader system claims remain out of scope.

## Context

Runtime behavior must not depend on parsing architecture prose. The current `RuleEngine` retains an `adr_dir` argument only for source compatibility; it does not parse ADR files into executable constraints.

## Decision

Executable local validation is defined by code:

- `RuleConfig.max_reflection_depth`
- `RuleConfig.entropy_threshold`
- `RuleConfig.max_content_chars`
- `RuleEngine.validate()` for node/content structure
- `RuleEngine.verify_stdlib_only()` for Python import-root membership in `sys.stdlib_module_names`

The default configuration is explicit in code and validated during construction.

## Consequences

Callers receive an inspectable local contract but remain responsible for deployment, authority, persistence, and claims outside the named implementation surface.

## Verification

Verification requires a named repository path, revision, fixture or store identity, command, environment, exit code, and retained failures. Documentary review alone is not runtime or semantic validation.

## Evidence boundary

`RuleEngine.validate()` establishes only the structural/content rules it implements.

`verify_stdlib_only()` parses Python source with AST and checks import roots against the current interpreter's standard-library inventory. It does not execute the program and is not a sandbox, malware detector, permission system, or semantic validator.

Changing an ADR or methodology does not change runtime behavior unless the executable code/configuration is separately changed.
