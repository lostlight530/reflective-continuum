# State continuity requires identity evidence

- Decision date: 2026-08-24
- Scope: reflective-continuum state, persistence, periodic research, and historical interpretation

## Status

Accepted for independent repository maintenance.

- Supersedes named ADR: `NONE`
- Related: ADR-003, ADR-004, ADR-006, ADR-009

## Context

The August 2026 R1/R2/R3/R4 history exposed several distinct continuity questions that cannot be answered from a path name, final value, graph hash, or later file presence alone.

Examples include:

- whether an R1 write and a later R2 read refer to the same database identity
- whether two repeated snapshot hashes describe the same durable state or merely the same rebuilt fixture
- whether a bare SQLite `:memory:` observation can be linked across independent connections, tasks, or processes
- whether a synthetic/test transition and an operational transition have the same origin class
- whether a later reconciliation file represents an original run or only a historical record
- whether an artifact present on `main` today was available to a Weekly snapshot when that snapshot executed

The 2026-08-06 R2 gap is the reference historical case: the current path exists because a reconciliation record was later added, while the original R2 runtime result remains unknown.

August R2 reports also explicitly record bare `:memory:` databases on multiple dates. A bare `:memory:` database is connection-local, so such observations cannot establish cross-task or cross-process persistence without additional identity evidence.

## Decision

A continuity claim MUST identify the continuity object and the evidence linking both sides of the claim.

Depending on the claim, the identity may be:

- database path plus connection/store identity
- durable database/file identifier plus schema/revision identity
- run/session/task identity
- graph/schema/revision identity
- event or transition origin identity
- artifact logical date plus generation/delivery history
- aggregation snapshot identity
- execution revision and evidence time

If the link cannot be established, use an uncertainty state such as:

- `PERSISTENCE_LINK_NOT_VERIFIED`
- `TRANSITION_ORIGIN_NOT_COMPUTED`
- `UNRESOLVED_DELIVERY_HISTORY`
- `HISTORICAL_RUNTIME_UNKNOWN`

Later path availability MUST NOT be used to manufacture an earlier execution result.

A successful current read MUST NOT, by itself, prove historical persistence through an unobserved interval.

A repeated graph/snapshot digest MUST NOT, by itself, prove memory continuity. It may show repeatability for a rebuilt deterministic fixture unless durable object identity is separately established.

R1 `ACCEPTED`, graph-write, or convergence language and R2 database observations MUST NOT be treated as observations of the same persistent state unless the storage/run identity link is verified.

## Consequences

Continuity and drift reports become narrower but distinguish observed state from inferred state. Weekly and monthly aggregation may summarize available evidence, but uncertainty survives aggregation unless new evidence directly resolves it.

A task-local `SUCCESS` can coexist with `PERSISTENCE_LINK_NOT_VERIFIED`, `INDETERMINATE_EMPTY_STATE`, or a separate task's failed/error result.

## Verification

Independent review checks that a continuity claim names the object identity, evidence source, time/revision boundary, and unresolved alternatives. Passing a current selfcheck remains evidence for the current checked state only.

For bare `:memory:` state, cross-run continuity remains unverified unless an explicit shared-store mechanism and identity evidence demonstrate otherwise.
